# 团队怎么提交 FAQ 修改

[返回首页](README.md)

## 同事只需提问题

现在即可：打开 Issues → New issue → FAQ 修改建议，填写：

1. 客户真正想解决的问题；已有答案不适用时，填写 FAQ 编号。
2. 适用产品、规格、控制方式和市场。
3. RFQ / 商品资料 / 测试记录的受限链接或内部编号；无法确认的地方写“待核验”。
4. 建议答案，以及为什么需要修改。
5. 建议仅内部使用，还是允许对外公开。

提交 Issue 不会立即改变 FAQ。不要把客户原始附件或身份信息复制到问答中。

## 维护者把建议整理成 PR

1. 检索已有 FAQ，能修订原答案就保留原编号，避免重复建条目。
2. 从最新默认分支新建分支，例如 `faq/update-control-options`。
3. 复制[条目模板](templates/faq-entry.md)，中文放 `zh-CN/`，英文放 `en/`；同一问答使用同一个编号。
4. 标记为 `draft`，记录依据、适用范围、是否可公开和未确定事实。
5. 打开 PR，默认会加载 FAQ 审核模板。也可查看[模板内容](../../.github/pull_request_template.md)。
6. PR 描述写明原答案、新答案、修改理由、关联 Issue；不要仅写“优化 FAQ”。
7. 请求 `kelvinchen1119` 审核。同一账号创建的 PR 无法再由该账号自我审批。

## Kelvin 审核时看什么

- 答案有没有产品资料或已确认业务规则支撑？无法证明的参数、认证、交期与兼容性仍保持待核验。
- 结论是否只适用于指定 SKU / 市场？中英文是否一致？
- 是否把普通款、小爱同学、Matter 误写成同一款同时具备的能力？
- 是内部培训答案，还是可以直接发给客户的公开答案？
- 修改是否影响原报价、税费、承诺或官网已发布口径？

通过后，由维护者在同一个 PR 中填写真实的 `reviewed_by`、`reviewed_at`，并将状态改为 `approved`。审核记录必须存在于实际 PR；不要预填审核通过。内容再次改动后需要重新审阅最终差异。

当前套餐不强制审核，因此团队成员仍需遵守“未获 Kelvin 同意不合并”。若需要系统保证，按[维护说明](GOVERNANCE.md)补齐规则。

## 每周整理一次 RFQ

建议每周指定维护者人工汇总一次新增 RFQ 和待处理 Issue：

- 优先处理重复出现、阻碍成交、旧答案失效的问题。
- 检查已有 Issue / PR，合并同义问题，保留原来源。
- 依据不足时继续收集资料，不把猜测写成正式答案。
- AI 可以归类、去重、起草和翻译；输出仍为草稿，由人工确认。

本样板没有设置定时任务。未来接入自动汇总时，自动化只创建候选 Issue / 草稿 PR，不自行审批、合并或发布。

## 网站发布

只有 `status: approved` 且 `audience: public_candidate` 的最终版本，才进入网站发布复核。中文与英文应成对检查。

发布人核对正文、产品范围与来源后，在维护记录中填写网站地址、发布时间、发布 commit / PR。GitHub 合并和 Odoo 上线是两个可分别追踪的动作。
